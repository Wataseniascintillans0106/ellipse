# 版本管理小抄

给未来的自己看的。忘了怎么操作就翻这里。

---

## 一、这套东西是干嘛的

GitHub 有两个用处，你用的是第二个：

1. ~~开源分享~~ —— 让别人下载你的代码（暂时不需要）
2. **版本管理** —— 每次改完存一个档，随时能翻回任何一个历史版本，知道"哪天改了什么、为什么改"

具体来说，它能帮你：

- 改出 bug 了，对比一下就知道**这次动了哪几行**
- 三个月后想不起来当时为什么这么写，翻提交说明就行
- 改废了，一键退回上一个能用的版本
- 电脑坏了，代码在 GitHub 上还有一份

**核心概念**：Git 会在你每次"提交"时，给整个项目拍一张**快照**。这些快照串成一条时间线，你可以在时间线上任意跳转。

## 二、日常循环（99% 的操作就这四步）

```
改代码  →  看 GitHub Desktop  →  写一句说明  →  Commit  →  Push
```

### 详细步骤

**1. 改代码**

用 VS Code 改 `assets/js/app.js` 之类的文件，改完保存。

**2. 打开 GitHub Desktop**

它会自动列出**哪些文件变了**。点左边任一文件，右边会显示具体改动：

- 🟢 绿色 = 新增的行
- 🔴 红色 = 删除的行

**这一步别跳过。** 养成"提交前扫一眼"的习惯，能拦住不少"我什么时候改了这个"的意外。

**3. 写提交说明**

左下角 **Summary** 框里写一句话，说清这次改了什么（怎么写见第四节）。

**4. Commit，然后 Push**

- 点蓝色按钮 **Commit to main** —— 在本机拍快照
- 点顶部 **Push origin** —— 把快照传到 GitHub

### Commit 和 Push 为什么要分开？

| 动作 | 在哪发生 | 作用 |
| --- | --- | --- |
| **Commit** 提交 | 只在你电脑上 | 本机存档，可以连着存好几个 |
| **Push** 推送 | 传到 GitHub | 上传存档，别人/别的设备才看得到 |

分开是有意设计的：你可以改一点提交一次、再改一点再提交一次，最后一起推上去。
**没 Push 的东西，GitHub 上就没有**，所以当天收工前记得推一下。

## 三、三条铁律（会真受伤的）

### 🚫 1. 永远别点 `Force push`（强制推送）

它会用你本地的内容**覆盖** GitHub 上的，把远程已有的提交直接抹掉。

看到任何带 `force` 字样的选项，**选"不"**。真需要用它的情况极少，等你完全明白后果了再说。

### 🚫 2. 别删项目里的 `.git` 文件夹

这个隐藏文件夹装着**全部修改历史**。它看着没用，其实是整个版本管理的心脏。

删了它，你的代码文件还在，但"什么时候改了什么"的记录全没了。

> 顺带一提：它也很大。你项目现在才 1.4MB，但 `.git` 文件夹会随着提交次数慢慢长大，
> 这是正常的，别当成垃圾删掉。

### 🚫 3. 固定在一个地方改代码

要么**只在电脑本地改**，然后推上去；要么**只在 GitHub 网页上改**，然后拉下来。

**别两边同时改同一个文件** —— Git 会不知道听谁的，产生"冲突"，处理起来对新手很烦。

你现在的做法是对的：**固定在本地改**。

## 四、提交说明怎么写

**原则：假设三个月后的自己完全失忆。**

| ❌ 别这么写 | ✅ 这么写 |
| --- | --- |
| `更新` | `新增：疼痛模块支持多个部位` |
| `fix bug` | `修复：未来日期仍可点击的问题` |
| `改了点东西` | `调整：设置页开关间距 12px → 16px` |
| `123` | `重构：把日期工具函数抽到 util.js` |

**推荐格式**：`类型：具体做了什么`

常用的类型词，四个就够：

- `新增：` 加了新功能
- `修复：` 修了 bug
- `调整：` 改了样式、文案、参数
- `重构：` 功能没变，但代码结构改了

**一次提交只做一件事。** 别把"改按钮颜色"和"修日期 bug"混在一条提交里——
将来想撤销其中一件时，才不会连累另一件。

## 五、出错了怎么救

初学者最大的心理负担是"怕改坏"。其实**几乎都能救回来**：

| 情况 | 怎么救 |
| --- | --- |
| 代码改乱了，**还没提交** | 左侧改动列表 → **右键那个文件** → `Discard changes`（丢弃更改）→ 立刻恢复成上次提交的样子 |
| **提交了**但马上后悔 | 上方 **History** 标签 → 右键那条提交 → `Undo commit`（撤销提交）→ 提交消失，但**改动还在**，可以继续改了再提交 |
| 想看看三天前是什么样 | History 里点任意一条提交，能看到当时每一行的改动 |
| 想拿回某个旧版本的文件 | History 里找到那条提交，右键 → `Revert changes in commit` |
| 想知道 GitHub 上现在是什么样 | 点顶部 **Fetch origin**，看看有没有别人（其实只有你）推的新东西 |
| 整个项目都改废了 | 从 GitHub 重新克隆一份，本地的随便折腾 |

> **一句话：只要 Push 过，你的东西就死不了。**
> GitHub 上那份就是你的后悔药。

## 六、这个项目的专属习惯

### 1. 提交前跑一遍自检

```bash
node scripts/smoke.mjs
```

跑完看到 **全部通过** 再提交。这是你的逻辑测试，能拦住不少低级错误。

想更仔细的话，起服务器后打开 <http://localhost:5173/scripts/flowcheck.html>，
它会在浏览器里真跑一遍交互（进记录页、展开栏、切区间等），把每条结果打在页面上。

### 2. 关于数据文件

项目里的 [.gitignore](../.gitignore) 已经设好了防线。**你在设置里导出的这些文件就算下载到这个文件夹，也绝不会被提交上去**：

- `ellipse-backup-*.json`（备份）
- `ellipse-records-*.md`（全部记录）
- `ellipse-summary-*.md`（区间汇总）
- `2026-09-27.md`（单日记录）

还有 `.corepack`、`node_modules` 这类缓存也一并被拦住了。

**你不需要每次提交前手动检查，这条防线是自动的。**

### 3. 换行符别管它

项目里有 [.gitattributes](../.gitattributes)，已经把 Windows / Mac 的换行符差异统一好了。
看到 Git 提示 `LF will be replaced by CRLF` 之类的警告，**忽略即可，不影响任何东西**。

## 七、常见疑问

**Q：我要不要学"分支"（branch）？**
A：**现在不用**。分支是多人协作时用的，你一个人开发，一直待在 `main` 分支上就对了。
GitHub Desktop 界面上会出现分支相关的按钮，暂时无视。

**Q：仓库是私人（private）的，算"开源"吗？**
A：不算。私人仓库只有你自己能看。
但你**随时可以改成公开**：仓库页面 → **Settings** → 拉到底部 **Danger Zone** → **Change visibility**。
改了之后，**之前所有的修改历史都会一起公开**，不用重来。

**Q：我的私人记录会跟着泄露吗？**
A：不会。记录只存在浏览器 localStorage 里，从来就不是项目文件。
项目里唯一跟"数据"有关的 [scripts/seed.html](../scripts/seed.html)，写的是用正弦函数生成的**假数据**。

**Q：API Key 会传上去吗？**
A：不会。它只存在你浏览器的 localStorage，永远进不了仓库。

**Q：多久提交一次比较好？**
A：**每完成一件小事就提交一次**。宁可碎一点，也别攒一天才提交——
攒太久的坏处是，万一改坏了，你分不清是哪一步改坏的。

**Q：忘了 Push 会怎样？**
A：代码只在你电脑上，GitHub 上还是旧的。电脑坏了就真丢了。
**每天收工前点一下 Push origin**，养成习惯。

## 八、术语小词典

| 词 | 中文 | 大白话 |
| --- | --- | --- |
| Repository / Repo | 仓库 | 你的整个项目，代码 + 全部历史 |
| Commit | 提交 | 给项目拍一张快照，存在本机 |
| Push | 推送 | 把本机的快照传到 GitHub |
| Pull / Fetch | 拉取 | 把 GitHub 上的拿到本机 |
| Branch | 分支 | 项目的平行版本，你现在用不着 |
| main | 主分支 | 默认那条主线，你一直待在这儿 |
| origin | 远程源 | GitHub 上那个仓库的代号 |
| Diff | 差异 | 这次改了哪几行（绿加红减） |
| Conflict | 冲突 | 两边改了同一处，Git 不知道听谁的 |
| Clone | 克隆 | 把 GitHub 上的项目整个下载到本机 |
